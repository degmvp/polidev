1. Purpose

The POLYDEV Operations & Maintenance environment centralizes PostgreSQL administration in a controlled Linux workspace.

Instead of relying on isolated manual commands, the environment uses documented scripts and repeatable procedures for database access, SQL execution, backup, restore, troubleshooting and operational recovery.

Repeatable
Same procedure, same result.
Predictable
Known inputs and controlled execution.
Recoverable
Backups and logs protect every operation.
Maintainable
Knowledge remains documented.

4. Environment Configuration

PostgreSQL connection parameters are centralized in env.sh. 

export PGHOST="aws-1-us-east-2.pooler.supabase.com"
export PGPORT="6543"
export PGDATABASE="postgres"
export PGUSER="postgres.PROJECT_REFERENCE"
export PGPASSWORD="YOUR_PASSWORD"

Load the environment after opening a new terminal:

source ./env.sh
Operational Note The client connects to the Supabase pooler through port 6543. PostgreSQL may report the internal server port as 5432. This is expected.
Security Warning Never publish env.sh with a real password in GitHub, documentation, screenshots or public repositories.

5. Script Reference

env.sh

Loads the PostgreSQL connection variables used by psql, pg_dump, pg_restore and the operational scripts.

qry.sh

Opens an interactive PostgreSQL session for administrative queries, metadata inspection and SQL execution.

backup_polydev.sh

Generates a timestamped PostgreSQL backup inside OM/backup and records execution information in OM/logs.

restore_polydev.sh

Lists available backups, asks for the complete backup file name, requests confirmation and performs a controlled restore.

restore_polydev_local.sh

Restores a POLYDEV backup into an isolated local PostgreSQL environment for validation, testing and recovery exercises.

Details King Production and testing must remain independent. A local restore environment protects production while allowing complete validation.

7. Backup Procedure

  1. Load the environment.
  2. Confirm connectivity.
  3. Execute the backup script.
  4. Wait for completion.
  5. Confirm the generated backup file.
cd /home/degsu/Compartilhado/OM/scripts
source ./env.sh
./backup_polydev.sh
ls -lh ../backup | tail

Example backup name:

polydev_20260803_155429.backup
Best Practice Confirm that the newest backup has a valid size. A zero-byte backup must never be considered operationally valid.

8. Restore Procedure

  1. Confirm the destination environment.
  2. Confirm that a valid backup exists.
  3. Run the appropriate restore script.
  4. Enter the complete backup filename.
  5. Review the destination confirmation.
  6. Execute the restore.
  7. Review the log and validate the database.
cd /home/degsu/Compartilhado/OM/scripts
source ./env.sh
./restore_polydev_local.sh
Production Warning Never use production as a restore test area. Restore must first be validated in an isolated local environment.

9. Linux Procedures

Convert CRLF to Unix

sed -i 's/\r$//' arquivo.sh

Grant execution permission

chmod +x arquivo.sh

Verify the interpreter line

head -n 1 arquivo.sh

Expected:

#!/bin/bash
Details King The message “bad interpreter” or “interpretador incorreto” usually indicates a Windows CRLF character after /bin/bash.

10. Production Protection

  • Never perform restore tests in production.
  • Never overwrite a validated backup without preserving another copy.
  • Never expose database credentials in public files.
  • Always verify the destination before running a restore.
  • Always keep logs for backup and restore operations.
  • Always validate the newest backup before maintenance.
Mandatory Rule No destructive operation starts without a recent, verified and recoverable backup.

Permission denied

chmod +x arquivo.sh

Environment not loaded

source ./env.sh

Wrong port

grep PGPORT env.sh
echo $PGPORT

Connection validation

psql
SELECT current_database(), current_user, inet_server_port();

Backup validation

ls -lh ../backup | tail

Current directory validation

pwd
ls -la
