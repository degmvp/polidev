Architecture

The technical structure of the POLYDEV Open Source Ecosystem: pages, database, viewers, content organization, grouping rules, GitHub Pages and Supabase integration.

“Architecture is not the number of technologies used. Architecture is the clarity of how they work together.”
Author: Degmar Barbosa Version: 1.0 Date: 2026-07-27 Status: Living Document
Chapter 00

Architecture Overview

POLYDEV uses a deliberately simple architecture composed of static web pages, a PostgreSQL database and dynamically loaded technical content.

The platform is designed to remain understandable, portable and inexpensive to operate.

The architecture avoids unnecessary frameworks and complex infrastructure when HTML, CSS, JavaScript and PostgreSQL can solve the problem directly.

UI

Static Front End

HTML, CSS and JavaScript hosted through GitHub Pages.

DB

PostgreSQL Data Layer

Supabase stores titles, categories, file paths, grouping keys and article content.

TXT

Portable Content

Technical articles remain available as text files inside the repository.

Architectural objective

The complete platform should be recoverable from the GitHub repository, database backup and documentation.

Chapter 03

Database Model

The central table is conteudos.

PostgreSQL 
CREATE TABLE conteudos (
  id           bigint generated by default as identity primary key,
  titulo       text,
  categoria    text,
  arquivo_url  text,
  downloads    integer default 0,
  ativo        boolean default true,
  programa     text
);
Column Purpose Example
id Unique database identifier. 1024
titulo Article title shown in menus and viewers. Worker Pool Architecture
categoria Series or content family. goeng
arquivo_url Relative location of the content file. downloads/go/goeng01.txt
downloads Download or access counter when enabled. 120
ativo Controls whether the content is available. true
programa Logical grouping key used by viewers and menus. 12
Database preservation rule

Never alter the meaning of an existing column without a documented migration plan and verified backup.

Chapter 05

Viewer Architecture

Viewers connect database metadata, grouped menus and technical article rendering.

A viewer typically performs the following operations:

Initialize the Supabase client.

Connect using the project URL and public anonymous key.

Query active content by category.

Retrieve only records belonging to the viewer’s technical series.

Order records predictably.

Preserve the expected article sequence instead of relying on random database order.

Group records by programa.

Build a clearer sidebar by presenting logical content groups.

Load selected article content.

Display the content without requiring a full page reload.

Maintain responsive navigation.

The menu must remain usable on desktop and mobile screens.

JavaScript Query Pattern 
const { data, error } = await supabase
  .from("conteudos")
  .select(`
    id,
    titulo,
    categoria,
    arquivo_url,
    programa,
    ativo
  `)
  .eq("categoria", category)
  .eq("ativo", true)
  .order("id", { ascending: true });

if (error) {
  throw new Error(error.message);
}
Chapter 06

Grouping Strategy

The programa column is a logical grouping key, not necessarily a program file name.

Series structure Example grouping Purpose
Pairs 01–02 → 12 Groups two related articles under one menu section.
Pairs 03–04 → 34 Maintains predictable progression.
Triples 39–41 → 80 Supports larger series without creating excessive sidebar sections.
Triples 42–44 → 81 Creates compact navigation for advanced phases.
Grouping principle

Grouping exists to reduce reader confusion. It must never be changed only to make database values look more elegant.

JavaScript Grouping 
function groupByProgram(records) {
  return records.reduce((groups, record) => {
    const key = record.programa || "ungrouped";

    if (!groups[key]) {
      groups[key] = [];
    }

    groups[key].push(record);

    return groups;
  }, {});
}

Chapter 08

Naming Conventions

Naming must be short, predictable and consistent within each series.

Element Pattern Example
Article code SERIES + sequential number HACK19
Text file Lowercase series code + number hack19.txt
Viewer Series or technical category hack.html
Database category Lowercase stable identifier hack
Banner Series name or publication phase hack_170.jpg
Documentation Lowercase chapter name architecture.html

Good naming

Short, stable, searchable and already aligned with the existing series.

Avoid

Renaming working files for personal preference or introducing multiple patterns inside the same series.

Chapter 09

Supabase Integration

Supabase provides the managed PostgreSQL database used by the POLYDEV platform.

The browser front end uses the Supabase JavaScript client to retrieve public application content.

JavaScript Initialization 
const supabaseUrl = "YOUR_SUPABASE_URL";
const supabaseAnonKey = "YOUR_PUBLIC_ANON_KEY";

const supabaseClient = supabase.createClient(
  supabaseUrl,
  supabaseAnonKey
);
Security rule

Database passwords, service-role keys and private credentials must never be placed inside public HTML, JavaScript files or GitHub repositories.

Browser

Uses only credentials explicitly intended for public client applications.

Administration

Uses PostgreSQL credentials through DBeaver, psql and protected environment files.

Backup

Uses pg_dump or database administration tools outside the public repository.

Chapter 10

GitHub Pages

GitHub Pages distributes the static application and preserves the version history of the public repository.

Production links must remain stable.

Existing published LinkedIn, YouTube and social media links depend on repository paths.

Test locally before publishing.

Verify page rendering, navigation, Supabase access and mobile behavior.

Test again in production.

Local success does not replace GitHub Pages validation.

Preserve repository history.

Commit changes with meaningful descriptions and avoid destructive rewrites.

Git Workflow 
git status

git add architecture.html

git commit -m "Add POLYDEV architecture documentation"

git push origin main
Chapter 11

Engineering Standards

Clone stable viewers before inventing new ones.

Reuse proven architecture and change only what the new series requires.

Separate visual identity from data logic.

CSS should control presentation while JavaScript controls loading and interaction.

Use database-driven navigation.

Avoid manually maintaining long lists when the database already contains the required metadata.

Preserve backward compatibility.

New phases should not break existing series, viewers or published URLs.

Validate production behavior.

A page is not homologated until it works from the public GitHub Pages URL.

Keep recovery possible.

Code, content, database and documentation must be backed up independently.

Chapter 12

Change Control

Structural changes must be deliberate, reversible and documented.

01
Observe

Understand the current behavior.

02
Backup

Protect code and database.

03
Change

Apply one controlled modification.

04
Test

Validate locally and in production.

05
Document

Record the final decision.

One change at a time

When multiple elements are changed simultaneously, the source of an error becomes harder to identify. POLYDEV troubleshooting should remain linear and evidence-based.
